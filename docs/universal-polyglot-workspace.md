# SymbolWright Universal Polyglot Workspace

This workspace separates three different meanings of “multilingual”:

1. **Programming-language support** — the editor can load starter code, syntax/editor ids, extensions, and honest capability metadata for many languages.
2. **Code intelligence** — SymbolWright can route generate, explain, review, test-proposal, translation, and semantic-drift tasks without claiming execution proof that did not happen.
3. **Human-language UI localization** — the workspace UI has real i18n resources. The UI language selector changes editor labels only; it does not change programming-language support.

## Executable vs edit-only

The Run/Preview button is enabled only when the selected language has a registered runner id. If a language is edit-only, the UI shows this exact message:

> This language currently supports editing, syntax highlighting, and AI assistance. Execution requires a configured sandbox runner.

That means Ruby, R, Java, Go, Rust, C++, C#, and the other compiled/interpreted languages are intentionally not presented as runnable until a real runner is installed, wired, and tested.

## Multi-file workspace sessions

The workspace now has a real session model in `src/workspace/workspace-session.ts` and a local browser persistence path in `/workspace`.

A session stores:

- session id, name, schema version, active file id, created/updated timestamps;
- multiple files;
- each file's name, language id, code, diagnostics, output, errors, dirty state, and timestamps.

The `/workspace` page supports:

- file tabs;
- new file;
- rename file;
- delete file while preserving the invariant that at least one file remains;
- per-file language selection;
- per-file output/errors/diagnostics preservation;
- dirty-state marker on edited files;
- autosave to browser `localStorage` under `symbolwright.workspace.session.v1`;
- export session JSON;
- import session JSON.

This is local browser persistence, not fake cloud storage. Clearing browser storage removes the saved session unless it was exported first.

## Project bundle import/export

The workspace also supports browser-local project bundle JSON through `src/workspace/workspace-project-bundle.ts` and `/workspace` controls.

A project bundle is not a ZIP file and does not write to a Git repository. It is a deterministic JSON shape:

```json
{
  "kind": "symbolwright.workspace.project-bundle",
  "schemaVersion": 1,
  "manifest": {
    "schemaVersion": 1,
    "projectId": "symbolwright-default-session",
    "name": "SymbolWright Workspace Session",
    "exportedAt": "2026-07-09T12:00:00.000Z",
    "files": [
      { "path": "main.js", "languageId": "javascript", "sizeBytes": 123 }
    ],
    "safetyWarnings": ["..."]
  },
  "files": [
    { "path": "main.js", "content": "console.log('hello')" }
  ]
}
```

The bundle implementation:

- exports the active local workspace session as a project-like file list;
- includes a manifest with paths, language ids, byte sizes, and safety warnings;
- deduplicates repeated file paths during export;
- imports bundle files back into a local workspace session;
- maps languages by extension when needed;
- rejects unsafe paths such as absolute paths, backslashes, and `..` traversal;
- rejects duplicate paths, unknown languages, mismatched manifests, oversized files, and oversized projects.

This keeps the browser workspace portable without pretending that SymbolWright has full repository write access from the browser.

## Browser runner limitations

JavaScript runs in a browser Worker generated by the workspace UI. The Worker wrapper captures console output, disables common network entry points inside the wrapper, has no DOM access, and is terminated after a short timeout. It is meant for small snippets, not untrusted multi-file applications.

SQL runs through the installed `sql.js` package in a browser Worker. The web server serves only two allowlisted sql.js assets:

```txt
/vendor/sql-wasm.js
/vendor/sql-wasm.wasm
```

The SQL runner creates a fresh in-memory SQLite database for each run. It does not expose persistent filesystem access. The Worker is terminated after the configured timeout, and result rows/cell sizes are capped before rendering. SQL output is rendered as a table in the workspace preview panel.

Python runs through Pyodide in a browser Worker. The Worker downloads the Pyodide browser runtime from the configured Pyodide distribution URL on first use, captures stdout/stderr, runs code through `runPythonAsync`, caps output, and is terminated if it exceeds the configured timeout. SymbolWright does not expose server-side Python execution in this runner.

HTML/CSS renders through a sandboxed iframe preview. It is a visual preview, not command execution.

## Server runner setup

The TypeScript runner uses the existing Node web server route:

```txt
POST /api/workspace/run
```

The server runner:

- creates a temporary workspace per run;
- writes the submitted TypeScript and compiled JavaScript under that workspace;
- transpiles with the installed TypeScript compiler;
- executes compiled JavaScript in a Node `vm` context;
- removes `require`, `process`, `Buffer`, `fetch`, timers, and interval APIs from the vm context;
- enforces a timeout;
- enforces a max output size;
- returns a structured success/syntax-error/runtime-error/timeout/unsupported result.

No other server-run language is exposed until a real sandbox runner and tests are added.

## AI code translation workflow

The code-intelligence router uses a structured translation flow:

1. Detect source language.
2. Confirm or infer target language from the dropdown.
3. Extract behavior/specification.
4. Generate target implementation.
5. Generate target-language tests.
6. Show semantic risks and assumptions.
7. Mark the result as `UNVERIFIED`, `TESTED`, or `FAILED`.

SymbolWright must never present translated code as proven equivalent unless tests actually run.

## Workspace-to-chat intelligence bridge

The workspace now exposes a real bridge endpoint:

```txt
POST /api/workspace/intelligence
```

The endpoint accepts the selected code, source language, optional target language, diagnostics, output, errors, task kind, and verification status. It returns:

- the structured code-intelligence task plan;
- a chat-ready prompt containing the selected code and workspace context;
- the suggested agent mode, either `READ_ONLY` or `PROPOSAL_ONLY`;
- a draft message payload that can be opened in the existing SymbolWright Chat UI.

The bridge does not call a provider by itself. It prepares the prompt and hands it to the real chat/agent surface, where the operator still connects with `SYMBOLWRIGHT_API_KEY`, chooses browser-only or API-backed mode, and decides whether to send the draft through `/api/chat` or `/api/agent`.

The SymbolWright Chat UI accepts workspace drafts through query parameters:

```txt
?draft=<encoded prompt>&agentMode=READ_ONLY
```

This keeps provider secrets out of the workspace page and avoids creating a second fake chat system.

## Cross-language equivalence harness

The starter equivalence harness includes deterministic examples for:

- factorial;
- fibonacci;
- palindrome;
- JSON transform;
- sort numbers;
- string normalization.

Each example stores a shared natural-language spec, source implementation, target implementation, test inputs, and expected outputs. The harness can mark observed outputs as `PASS`, `FAIL`, or `UNVERIFIED`.

## Human-language UI localization

The workspace has separate English and Spanish resource files in TypeScript. The language selector changes UI labels only. It does not alter language capability, runner availability, or code-generation semantics.

## Codespaces run instructions

```bash
set -euo pipefail

npm install
npm run typecheck
npm run lint
npm test
npm run build

export SYMBOLWRIGHT_API_KEY=$(openssl rand -hex 16)
npm run serve
```

Open the forwarded port for `8787`, then use the **Workspace** tab in the
nav (or visit `/#/workspace` / `/workspace`, which redirects there). The
Workspace and Agent are tabs in the same page now, not separate
dashboard/chat servers on separate ports.

Choose a code-intelligence task in the Workspace tab and it switches
straight to the **Agent** tab with the draft pre-filled, in the same page
&mdash; no separate chat server to start, no new tab to open.

## Troubleshooting: Run button disabled

The Run/Preview button is disabled when:

- the selected language is `edit-only`;
- the selected language is `data-viewer`;
- the selected language has no registered runner id;
- the language would require a sandbox/toolchain that is not installed and tested.

That is intentional. Add a real runner, register it in the language registry, and add runner tests before marking a new language executable.

## Troubleshooting: session did not persist

Sessions are stored in browser `localStorage`. Persistence can fail or disappear when:

- browser storage is cleared;
- the workspace is opened in a private/incognito browser session;
- a different browser/device is used;
- an imported session JSON is invalid.

Use **Export session JSON** before clearing storage or switching devices.

## Troubleshooting: project bundle did not import

Project bundle imports can fail when:

- the JSON is not a `symbolwright.workspace.project-bundle` bundle;
- the manifest file list does not match the bundle file list;
- a path is unsafe or duplicated;
- a language id is unknown;
- file/project size limits are exceeded.

Fix the bundle JSON and import it again. Importing a bundle only updates the local browser workspace session; it does not write files into the repository.
